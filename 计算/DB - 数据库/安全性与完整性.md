## 安全目标

数据库安全保护机密性、完整性和可用性。威胁既来自未授权访问，也来自已授权用户越权、应用漏洞、配置错误和内部滥用。

安全控制应遵循最小权限、职责分离、默认拒绝和可审计原则。

## 身份认证与授权

身份认证确认主体是谁，授权决定主体可以对哪些对象执行哪些操作。SQL 可用 `GRANT` 与 `REVOKE` 管理表、列、视图和过程权限。

角色把权限组织为职责集合，再把角色授予用户，避免逐用户维护。视图和存储过程可隐藏敏感列或限制可执行操作。

> [!danger] 应用用户不应拥有数据库管理员权限
> 应用连接账号只授予完成业务所需的最小权限；模式迁移、备份和审计使用独立身份，降低凭据泄漏后的影响范围。

## SQL 注入与参数化

把外部输入拼接进 SQL 会让数据被解释为语法，产生 SQL 注入。参数化查询把语句结构与参数值分离，是首要防线；输入校验、最小权限和审计提供纵深保护。

对动态表名、排序列等不能直接参数化的标识符，应使用白名单映射，而非转义任意用户文本。

## 审计与加密

审计日志记录主体、时间、对象、操作和结果，用于追责与异常检测。审计日志自身应防篡改并限制访问。

传输加密保护客户端与数据库之间的数据，静态加密保护磁盘或备份泄漏；密钥管理决定加密系统的实际安全性。加密不能替代权限控制和应用层数据最小化。

## 完整性约束

+ **域完整性**限制属性类型、范围与格式。
+ **实体完整性**要求主码唯一且非空。
+ **参照完整性**要求外码为空或引用存在的候选键。
+ **用户定义完整性**表达业务特有规则。

约束可由 `NOT NULL`、`UNIQUE`、`CHECK`、`PRIMARY KEY` 和 `FOREIGN KEY` 声明。声明式约束由 DBMS 在所有写入路径统一执行，通常优于只在某个应用中检查。

## 触发器与断言

跨行、跨表规则有时需触发器或过程实现。触发器隐式执行，必须防止递归触发、次序依赖和大范围扫描；能由键、外码和 `CHECK` 表达的规则不应不必要地改用触发器。

完整性检查需要位于事务中，避免「先检查、后写入」之间被其他事务改变条件。

> [!note] 安全性与完整性的区别
> 安全性回答「谁可以做什么」，完整性回答「允许存在什么数据状态」。权限正确不保证业务数据有效，数据满足约束也不表示访问经过授权。

## 为什么需要异常

传统错误码要求每一层显式检查并转发，容易使正常逻辑与错误处理交织。全局错误变量还会引入同步、复位和遗漏检查问题。

**异常处理 (exception handling)** 把异常发现与恢复策略分离：底层代码在无法完成契约时抛出异常，调用链上能恢复的层捕获并处理。

## `throw`、`try` 与 `catch`

```cpp
double triangle_area(double a, double b, double c)
{
    if (a <= 0 || b <= 0 || c <= 0 || a + b <= c || b + c <= a || c + a <= b) {
        throw std::invalid_argument("invalid triangle sides");
    }
    const double s = (a + b + c) / 2.0;
    return std::sqrt(s * (s - a) * (s - b) * (s - c));
}
```

调用者可在 `try` 块中执行操作，并用类型匹配的 `catch` 处理：

```cpp
try {
    use(triangle_area(a, b, c));
} catch (const std::invalid_argument& error) {
    report(error.what());
}
```

异常通常按 `const` 引用捕获，以保留动态类型并避免复制。派生异常的处理器应写在基类处理器之前。

## 传播与栈展开

抛出异常后，运行时沿调用栈寻找匹配的处理器。离开各作用域时，已完成构造的自动对象按逆序析构，这一过程称为**栈展开 (stack unwinding)**。

若一直没有匹配处理器，程序调用 `std::terminate`。若在栈展开期间析构函数再次抛出异常，也会导致终止，因此析构函数不应传播异常。

> [!note] RAII 是异常安全的基础
> 栈展开只会自动析构对象，不会替程序员释放裸资源。把资源放入 RAII 对象，才能让正常返回与异常路径共享可靠清理。

## 标准异常层次

`<stdexcept>` 提供常用异常类型：

+ `std::invalid_argument` 表示参数值不满足要求。
+ `std::out_of_range` 表示索引或范围越界。
+ `std::runtime_error` 表示只能在运行时发现的一般失败。
+ `std::logic_error` 表示程序逻辑或接口使用错误。

抛出的异常应描述失败类别，而不是把所有错误都压成字符串。自定义异常可继承合适的标准异常，并携带结构化上下文。

## 异常安全保证

函数在异常发生时可提供不同保证：

+ **不抛保证**：函数不会抛出异常。
+ **强保证**：失败时可观察状态保持不变，操作具有事务性。
+ **基本保证**：对象仍有效且无资源泄漏，但状态可能改变。
+ **无保证**：失败后状态可能不可用。

强保证常用「先构造临时结果，全部成功后再交换提交」实现。

> [!tip] 先完成再提交
> 读取、分配和验证都可能失败时，先在局部临时对象中完成操作，最后用不会抛异常的交换更新目标，可显著简化回滚。

## 何时使用异常

异常适合报告当前层无法按契约完成、且调用者可能在较高层恢复的失败。正常分支、循环终止和可预期的查询结果不应依赖异常控制。

低层库不应擅自打印错误或终止进程；它应返回可检查结果或抛出有语义的异常，把用户交互策略留给边界层。

## `noexcept`

`noexcept` 表示函数承诺异常不会逃逸。若承诺被违反，程序终止。析构函数、交换函数和移动操作在确实不会抛时标记 `noexcept`，有助于容器选择更安全高效的实现。

`noexcept` 不是简单的性能标签，只有实现及其调用的全部操作都满足承诺时才能使用。

## 捕获与重新抛出

处理器可记录上下文后用 `throw;` 重新抛出当前异常，并保留其动态类型。写 `throw error;` 会抛出一个新副本，可能产生切片。

只捕获自己能够处理或能增加有用上下文的异常。空的通用 `catch (...)` 会隐藏故障，应只用于清理、边界隔离或转换为明确错误协议。

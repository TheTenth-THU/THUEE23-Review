# 组织课程知识

把来源各异、顺序各异的课程材料整理成概念连贯、可检索、可复习且经过验证的 Obsidian Markdown 文件组。把源材料的目录视为证据线索，不要直接当作最终知识结构。

## 协调项目规则和其他技能

+ 先读取仓库根目录 `AGENTS.md` 和目标课程现状；以 `AGENTS.md` 作为文件格式、语言、公式、Callout 和链接规范的最终依据。
+ 输入包含 PDF 时，同时使用 `pdf` skill；涉及公式、图形或版面时渲染相关页面，不要只依赖文本提取。
+ 输入包含 `.tex` 时，同时使用 `latex-to-markdown` 和 `latex-macros`；由本技能决定知识结构和内容取舍，由两个 LaTeX 技能处理语法、宏、图片与 TikZ 转换。
+ 不要把临时覆盖表、来源清单或工具状态提交为课程正文。

## 选择任务模式

开始前明确采用一种主模式，必要时组合使用：

+ **新建**：从 `raw/` 建立知识地图、README、父子章节和正文。
+ **补全**：维持合理的既有结构，补足缺失知识、推导、解释、例题或链接。
+ **重构**：重新判断知识主线、章节边界和父子层级，再迁移并改写内容。
+ **增量更新**：识别新资料影响的知识单元，只更新受影响章节并回修父级概要。
+ **审计**：只报告内容、结构和验证问题；除非用户要求修复，否则不要改写正文。

## 执行工作流

### 1. 盘点课程与来源

读取目标课程的 `README.md`、`QUESTIONS.md`、根目录章节、`raw/` 和 `res/`。记录已有场景、孤立文件、父子章节、资料覆盖、符号体系和明显缺口。先按任务模式决定读取深度：结构审计和重构规划默认盘点全部文件名、抽查代表正文与来源，不要逐份精读 `raw/`；只有完整提取或覆盖核验才按知识单元系统精读来源。处理多来源或冲突材料时，读取 [来源提取与综合](references/source-synthesis.md)。

不要根据静态说明推断课程进度。不要在尚未理解现状时批量改名或拆分文件。

### 2. 建立知识地图

先提取概念、问题、模型、定理、方法和应用，再建立三类关系：

+ **依赖关系**：理解当前知识前必须掌握什么。
+ **推导关系**：结论由哪些条件、定义或机制得到。
+ **应用关系**：知识用于解释什么现象或解决什么问题。

用这些关系确定学习顺序。不要机械复制教材页序、课件课次或 LaTeX 的 section 边界。

重构任务必须主动打破旧文件边界：先忽略原始出现位置，独立写出课程的并列主干、共享理论和概念级叶节；再建立「旧标题 → 新职责文件」迁移表。如果新层级仍能与课件课次或旧文件一一对应，必须额外证明这是知识结构本身导致，而不是惰性沿用。

### 3. 设计文件层级

为课程建立从 README 到父章节、子章节和知识单元的层级。需要判断拆分、合并或父章节时，读取 [分节与层级判断](references/splitting-heuristics.md)。

先形成拟议的 `scenes` 和每个文件的一句话职责，再开始大规模写作。重构已有课程时，先说明结构变化及迁移范围，避免在判断未稳定时反复移动内容。

设计 `scenes` 时同时执行以下职责测试：

+ **顶层分支测试**：顶层必须是课程内部真正并列的研究对象或问题族，不得用「基础」「方法与应用」等可套用于任意课程的空泛标题代替学科分类。
+ **同层一致测试**：同一父章节下的子章节应使用同一分类维度，不得把数据对象、求解算法、应用场景和工具混为同层。
+ **完整复习单元测试**：最低层不追求「一个名词一个文件」，而要围绕一个核心对象或问题形成定义、表示、直接方法、典型应用和权衡的解释闭环。对象的直接变体、典型实现和强绑定算法通常应保留在同一文件。
+ **阅读局部性测试**：模拟用户复习一个典型问题。若需在多个短文件之间反复往返才能同时看到数据表示、运行状态、核心算法和复杂度，说明拆分过度，应优先合并或就近安排。
+ **共享内容上提测试**：被多个子章节使用的定义、符号、前提、评价维度和通用方法，放入最低的共同层级。该层级可以是同一文件内的高层标题，不应把「上提」机械理解为「新建一个 scene」。
+ **父章节实质性测试**：父章节必须说明共同对象、分类标准、共享理论与子章节关系；仅列出 Wikilink 的导航页不足以支撑一层 `scenes` 结构。

### 4. 撰写知识单元

根据学科读取 [领域组织模式](references/domain-patterns.md)。每个核心知识单元按实际需要形成以下解释闭环：

1. 说明要解决的问题或引入动机。
2. 给出直观解释和正式定义，保留成立条件。
3. 展开关键推导、证明思路或运行机制。
4. 解释公式、结构或算法的含义，而不只陈列结果。
5. 连接相邻概念、典型应用、适用边界或常见误区。

不要机械套用五段结构。只保留对理解、推导、辨析或解题有贡献的内容。Callout 用于形式化定义、关键定理、典型例题和重要警告，不要把普通正文全部装入 Callout。

#### 面试回忆题整理

处理课程 `QUESTIONS.md` 时，先逐份核对面经来源、面试组名称和原题边界，再按知识点聚类。它必须是 `README.md` 中 Longform `scenes` 的首项，但仍严格采用仓库 `AGENTS.md` 的「面试回忆题（QUESTIONS.md）」专用格式；其中默认收纳的「分析与解答」Callout 是普通章节 Callout 规则的明确特例。

来源没有明确出现的追问不得补写成原题，可以放入「拓展」。题目是否合并以答案能否形成同一解释闭环为准：若各问只共享宽泛主题而解答明显割裂，应拆题。关联链接必须落到实际存在的课程笔记及尽可能精确的内部标题；没有对应笔记时记录覆盖缺口，不得链接问题自身或制造虚假关联。

### 5. 自下而上回修

完成子章节后重新阅读实际正文，执行以下操作：

+ 修正父章节概要，使其准确概括子章节的知识链。
+ 更新 README 的 `scenes`、课程知识主线、重点结构和复习指引；确认 `QUESTIONS` 位于 `scenes` 首位且未被忽略。
+ 补充必要的章节 Wikilink 和块链接，删除重复说明与失效链接。
+ 确认概念在首次使用前已经定义，或提供到定义位置的链接。

### 6. 验证内容和结构

读取 [质量量表](references/quality-rubric.md)，按其中的硬性门槛和内容维度复核。运行：

```powershell
powershell -ExecutionPolicy Bypass -File .agents/skills/organize-course-knowledge/scripts/audit-course-notes.ps1 -CoursePath '<课程目录>'
```

把脚本结果当作确定性结构检查和离群提示，不要把行数或 Callout 密度当作质量结论。存在原始 PDF 或编译 PDF 时，抽查核心定义、关键公式、图形和易错推导，并检查 Obsidian 实际渲染。

### 7. 交付

说明结构选择、知识取舍、修改文件、来源覆盖和验证结果。明确列出未核对资料、来源冲突、缺失附件、渲染限制和需要用户决定的内容。

## 判断原则

+ 优先保证知识依赖与解释闭环，再优化篇幅和视觉格式。
+ 区分事实、来源陈述、推断和建议；资料不足时标记缺口，不要补写成事实。
+ 保留目标课程已经稳定的符号和术语；统一前先检查跨章节用法。
+ 只改动任务范围内的文件；尊重用户已有内容和未提交修改。
+ 将仓库样例视为方法参考而非规范真值。需要对照现有课程时，读取 [仓库样例](references/repository-exemplars.md)。
